# 04：持久任务与可靠执行链路

状态：CODE_READY / POSTGRES_VERIFICATION_PENDING / REMOTE_PLATFORM_VERIFICATION_PENDING。产物类型：Runtime / Memory / Workflow。目标是让调查和动作在进程崩溃、重复投递、网络不确定及并发执行下保持可恢复、可解释。

读 [入口](./README.md)、[共享契约](./00-总体设计与共享契约.md)、[03](./03-身份授权与审批治理链路.md)及其交接。

源码必读：`packages/commerce-agent/src/recovery/`、`execution/`、`approvals/state-machine.ts`、`approvals/repository.ts`、`tests/recovery.test.ts`、`tests/approval-execution.test.ts`、`evals/failure-injection.ts`，以及 01—03 新增的任务/存储/授权代码。

进入条件：PostgreSQL 集成测试通过，03 可信主体与审批策略可调用，01 任务入口可由非 UI 进程驱动。

## 2. 业务结果与范围

支持任务排队、至少两个调查 Worker 竞争、人工等待、取消/超时、断点恢复，以及审批后异步动作和对账。平台动作首轮接独立 HTTP 测试服务，数据与业务库独立，模拟延迟可见和结果丢失。

首轮动作聚焦 ADJUST_AD_BUDGET 与测试工单创建。保留本地 MockExecutor 用于快速回归；网络测试平台是新增验证环境，不能称真实广告平台。

不宣称通用 exactly-once。采用至少一次任务投递、业务幂等、状态条件更新及 UNKNOWN 对账；无法判定的副作用停止自动重发并交人工处理。

## 4. 执行任务

### 04.1：持久队列与并发控制

- [x] 实现 jobs 表和短事务领取，PostgreSQL 使用 `FOR UPDATE SKIP LOCKED`；task/run/attempt 分层，不把同一任务重试伪装成新业务任务。
- [x] 租约含 owner、leaseUntil、递增 epoch；心跳、checkpoint 与完成提交均检查 epoch，失去租约的 Worker 不能覆盖接管者结果。
- [x] 队列设置 tenant 公平性、每租户并发上限、重试时间、最大次数与人工处理队列，防止一个租户耗尽额度。
- [x] Worker 通过 AbortSignal 优雅停止领取；在途取消与租约丢失触发协作中止，无有效租约不能提交结果。

### 04.2：事务事件、断点与恢复

- [x] 创建任务、审批状态变化和 Outbox 事件原子提交；派发重复允许，消费方按事件/业务键去重。
- [x] 复用 01 的 run event/checkpoint/manifest，并在 durable job 增加可 fencing 的跨进程 checkpoint。
- [x] 保留只读工具预算重试和模型 usage 语义；不承诺 token exactly-once。
- [x] 从最新已提交边界恢复，job attempt/epoch 与 task/run 身份分离，保留原证据与父子关系。
- [x] 区分 WAITING_INPUT、审批和 MANUAL_REVIEW；补充信息继续使用 01 已验证的 taskVersion 契约。

### 04.3：发送前记账与远端幂等

- [x] 新增 ActionExecutor 端口和 ReliableExecutionService，保留旧 MockExecutor 仅作回归兼容；DB 事务只处理本地状态和台账。
- [x] 审批策略和目标条件通过后，先持久化 requestId/idempotencyKey/参数摘要和 PREPARED 意图，再发送网络请求。
- [x] 独立 HTTP 测试平台支持幂等键和 expectedVersion，重复键不同 payload 拒绝；执行记录存于独立 SQLite。
- [x] PREPARED/SENT/UNKNOWN 状态覆盖发送前与发送后崩溃窗口；租约 fencing + 远端幂等/版本条件防止旧 Worker 覆盖。
- [x] HttpActionExecutor 对写请求不做自动重试，executor capabilities 决定对账策略。
- [x] target 版本校验在远端与变更同一事务内原子执行，过时版本零副作用。

### 04.4：UNKNOWN 与取消

- [x] Lookup 区分 APPLIED、REJECTED、PENDING、NOT_FOUND、UNAVAILABLE；NOT_FOUND 权威性和可见性窗口由 capabilities 明示。
- [x] 非权威 NOT_FOUND/UNAVAILABLE 保持 UNKNOWN，以有上限的指数退避推进，超过次数/期限转 MANUAL_REVIEW。
- [x] 无外部 operationId 时仍使用预先持久化的 requestId/idempotencyKey 查找，不凭本地变量判定远端未执行。
- [x] 队列取消可阻止未发送动作；在途写操作仅设 cancelRequested 并保留对账，不伪造 CANCELLED 结果。
- [x] 补偿被定义为新提案/新审批；系统不自动改写原 APPLIED 记录。

## 5. 验证矩阵

| 故障点 | 观测与硬门槛 |
| --- | --- |
| 两个真实 Worker 领取同任务 | 一个有效租约；旧 epoch 不能提交 |
| Outbox 派发前后杀进程 | 事件不丢失，重复投递不重复业务效果 |
| 调查中断后重启 | 已提交证据/状态复用，过期证据刷新 |
| 远端成功后断开连接 | UNKNOWN；按请求标识查得结果 |
| 远端结果延迟可见 | 暂时 NOT_FOUND 不标 FAILED，不盲重发 |
| 收到成功响应、提交 DB 前 SIGKILL | 接管并对账，只有一次外部业务效果 |
| 丢租约的 Worker 恢复并发发送 | 幂等/目标条件保护；本地 fencing 不被夸大为远端锁 |
| 远端无幂等能力且结果不明 | 禁止自动重发，明确人工处理 |
| 数据库不可用、模型挂起、取消 | 停止新调用/新副作用，保留可恢复状态 |

## 8. 详细执行设计

### 8.1 输入与输出

| 链路 | 输入 | 持久化输出 | 终端输出 |
| --- | --- | --- | --- |
| 调查任务 | tenant/shop/task/version/budget | `commerce_jobs(INVESTIGATE)`、Outbox、checkpoint | SUCCEEDED / WAITING_INPUT / RETRY_WAIT / MANUAL_REVIEW |
| 审批后动作 | proposal + 最新有效审批 + EXECUTOR 主体 | `commerce_jobs(EXECUTE)`、`commerce_execution_requests` | 远端 APPLIED / REJECTED / UNKNOWN |
| 对账 | requestId/idempotencyKey + executor capability | lookup 次数、nextLookupAt、远端 operationId | SUCCEEDED / FAILED / UNKNOWN / MANUAL_REVIEW |
| 取消 | jobId + 当前状态 | cancelRequestedAt 或 CANCELLED | 未发送可取消；已发送继续对账 |

### 8.2 接口与状态

`DurableJobRepository` 对外提供 `enqueue/claim/heartbeat/checkpoint/succeed/retry/manualReview/requestCancel/recoverExpired`。工作者领取后获得 `(jobId, leaseOwner, leaseEpoch, leaseUntil)`；续租和终态提交必须同时匹配 owner + epoch + 未过期租约。每次重新领取 epoch 递增，旧 Worker 恢复后无权覆盖新 Worker。

Job 状态机：

```text
READY/RETRY_WAIT -> LEASED -> SUCCEEDED
                         |-> RETRY_WAIT -> LEASED
                         |-> WAITING_INPUT
                         |-> MANUAL_REVIEW
READY/RETRY_WAIT -> CANCELLED
LEASED --cancel requested--> handler cooperative stop; 已发送动作转 RECONCILE
```

`ActionExecutor` 只暴露 `capabilities()`、`execute(request, signal)` 和 `lookup(requestId, signal)`。查询结果为 `APPLIED | REJECTED | PENDING | NOT_FOUND | UNAVAILABLE`；capability 显式声明幂等支持与 NOT_FOUND 是否权威。

Execution Request 状态机：

```text
PREPARED -> SENT -> APPLIED
                -> REJECTED
                -> UNKNOWN -> APPLIED/REJECTED/MANUAL_REVIEW
PREPARED -> CANCELLED
```

`PREPARED` 表示可安全首发；`SENT/UNKNOWN` 必须先 lookup，不得因本地重试直接重发写请求。

### 8.3 事务边界

1. 创建业务对象 + job + outbox 在同一个短事务内提交。
2. claim/续租/终态提交仅包含 SQL，模型调用和 HTTP 不在事务中。
3. 执行前校验提案、审批、权限和过期时间，原子写入 PREPARED 且将提案转 EXECUTING。
4. 网络调用前将请求标记 SENT；调用后另开短事务记录结果。SENT 后的任何异常都是 UNKNOWN，不能推断未执行。

## 11. 测试断言

- T01：两个 Worker 不能同时持有同一 job 的有效租约。
- T02：租约过期后可接管，epoch 增加，旧 owner 心跳/完成均返回 false。
- T03：达到 maxAttempts 进 MANUAL_REVIEW，不形成永久重试。
- T04：同一 tenant 达到并发上限时，其他 tenant 仍能被领取。
- T05：未领取 job 可取消；在途 job 仅设 cancelRequested，无伪终态。
- T06：旧 epoch 不能写 checkpoint 或发送 outbox 终态。
- T07：平台已应用但响应丢失时，本地 UNKNOWN，lookup 后 SUCCEEDED，远端效果数仍为 1。
- T08：延迟可见的 NOT_FOUND 保持 UNKNOWN，不发起第二次 POST。
- T09：同幂等键不同 payload 被远端拒绝，expectedVersion 过时无业务修改。
- T10：无幂等且无可靠 lookup 的不确定请求直接 MANUAL_REVIEW。
- T11：审批人权限在执行前被撤销时，不生成远端请求。
- T12：新增专项通过，01—03 全量回归无退化，类型检查通过。
