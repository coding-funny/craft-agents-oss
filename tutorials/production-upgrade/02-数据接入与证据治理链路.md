### 8.2 固定实现选择

1. 导入入口只接受宿主指定的 manifest 文件；模型工具不能传文件路径、连接串、tenant 或 shop。
2. 首版支持 JSON、JSONL 和 CSV。五类 canonical record 均由现有 Zod Schema 解析；未知字段、非法行和币种冲突进入 quarantine，不能静默丢弃。
3. 导入分 `dry-run` 与 `apply`。`apply` 在单事务内完成批次、版本记录、快照和游标推进；失败不产生可查询快照。
4. 去重键为 `tenantId + shopId + kind + sourceRecordId`；内容哈希相同为 duplicate，变化为 revision 并保留历史版本。
5. snapshot 为不可变记录集合。调查开始前绑定一个 snapshotId，同一 Run 不随后台新导入漂移；未绑定时由宿主按 `asOf` 解析一次后固定。
6. PostgreSQL 使用 Bun 内置 `SQL` 驱动，避免增加重复客户端依赖；SQLite 作为本地合同实现。生产配置缺失或连接失败时禁止静默回退 SQLite。
7. 当前环境没有 `docker`、`podman` 或 `psql`。因此 PostgreSQL migration/driver/合同可完成，真实 PostgreSQL 迁移、回滚、重启验收必须保持 `BLOCKED_EXTERNAL`，直到提供 `COMMERCE_TEST_DATABASE_URL`。
8. 示例数据必须标记 `SYNTHETIC_FIXTURE`。没有授权记录时不得将其描述为真实商家数据。

## 9. 输入、输出、接口与状态

### 9.1 导入清单

```ts
type DataKind = 'sales' | 'inventory' | 'promotions' | 'products' | 'ads';
type SourceType = 'AUTHORIZED_EXPORT' | 'SYNTHETIC_FIXTURE' | 'HTTP_TEST_SOURCE';

type ImportManifest = {
  schemaVersion: 1;
  source: {
    sourceType: SourceType;
    sourceId: string;
    owner: string;
    authorizationRef?: string;
    exportedAt: string;
  };
  scope: {
    tenantId: string;
    shopId: string;
    currency: string;
    timezone: string;
  };
  businessWindow: { start: string; end: string };
  mappingVersion: string;
  metricDefinitionVersion: string;
  files: Array<{
    kind: DataKind;
    path: string;
    format: 'json' | 'jsonl' | 'csv';
    sha256: string;
    schemaVersion: 1;
  }>;
};
```

运行时严格解析且拒绝额外字段。`AUTHORIZED_EXPORT` 必须包含非空 authorizationRef；`SYNTHETIC_FIXTURE` 不允许伪造该字段。相对文件路径只能解析到 manifest 所在目录内，`..`、符号链接越界和绝对路径默认拒绝。摘要不匹配在读业务行前失败。

### 9.2 批次、记录版本与快照

```ts
type ImportStatus =
  | 'PENDING' | 'VALIDATING' | 'APPLIED'
  | 'PARTIAL' | 'REJECTED' | 'ROLLED_BACK';

type ImportBatchResult = {
  importId: string;
  status: ImportStatus;
  snapshotId?: string;
  accepted: number;
  revised: number;
  duplicates: number;
  quarantined: number;
  completeness: Record<DataKind, 'complete' | 'missing' | 'partial'>;
  issues: Array<{ kind: DataKind; row: number; code: string; message: string }>;
};

type DataRecordVersion = {
  recordVersionId: string;
  tenantId: string;
  shopId: string;
  kind: DataKind;
  sourceRecordId: string;
  version: number;
  contentHash: string;
  payload: unknown;
  businessTime: string;
  ingestedAt: string;
  importId: string;
};

type DataSnapshot = {
  snapshotId: string;
  tenantId: string;
  shopId: string;
  asOf: string;
  importId: string;
  recordVersionIds: string[];
  completeness: Record<DataKind, 'complete' | 'missing' | 'partial'>;
  metricDefinitionVersion: string;
  createdAt: string;
};
```

状态迁移固定为 `PENDING -> VALIDATING -> APPLIED|PARTIAL|REJECTED`，仅 APPLIED/PARTIAL 可产生 snapshot。只要 manifest/摘要/scope 级错误出现，整批 REJECTED；行级错误可隔离并得到 PARTIAL。ROLLED_BACK 是逻辑撤销标记，不物理删除已被报告引用的版本。

### 9.3 异步仓库端口

```ts
interface DataGovernanceRepository {
  transaction<T>(work: (tx: DataGovernanceTransaction) => Promise<T>): Promise<T>;
  getImport(importId: string): Promise<ImportBatchResult | undefined>;
  resolveSnapshot(scope: { tenantId: string; shopId: string; asOf: string }): Promise<DataSnapshot | undefined>;
  getSnapshot(scope: { tenantId: string; shopId: string; snapshotId: string }): Promise<DataSnapshot | undefined>;
}

interface DataGovernanceTransaction {
  createImport(input: CreateImportInput): Promise<void>;
  appendRecord(input: AppendRecordInput): Promise<'accepted' | 'revised' | 'duplicate'>;
  appendQuarantine(input: QuarantineInput): Promise<void>;
  commitSnapshot(input: CommitSnapshotInput): Promise<DataSnapshot>;
  rejectImport(importId: string, issues: ImportIssue[]): Promise<void>;
}
```

所有方法必须显式带 scope 或从事务绑定 scope；禁止只按 recordId/snapshotId 查询。PostgreSQL 与 SQLite 实现运行同一合同测试。

### 9.4 Adapter 与治理后的证据

`ImportedDataAdapter` 构造时接收 `{ tenantId, shopId, snapshotId }`，随后实现 01 的五个查询方法。查询中的 shop 必须与绑定 scope 一致，SKU 与窗口继续由 01 dispatcher 限制。返回 source 采用 `import:<sourceId>:snapshot:<snapshotId>`，warnings 明确缺失数据类型和 freshness。

`EvidenceRecord` 以可选字段兼容旧数据，并对新导入证据要求以下字段齐全：

```ts
type EvidenceGovernance = {
  schemaVersion: 2;
  tenantId: string;
  shopId: string;
  snapshotId: string;
  sourceType: SourceType;
  sourceRecordIds: string[];
  metricDefinitionVersion: string;
  contentHash: string;
  businessTimeRange: { start: string; end: string };
  ingestedAt: string;
};
```

新 evidenceId 的稳定输入包含 tenant/shop/snapshot/tool/规范化 query/sourceRecordIds/content；同内容跨店铺不得碰撞。`getEvidence` 必须用 tenant/shop 作用域查询，旧无 scope API 仅保留给旧 demo 且不能用于新调查。

### 9.5 Freshness、完整性与语义复核

```ts
type EvidenceHealth = 'FRESH' | 'STALE' | 'INCOMPLETE' | 'CONFLICT';
type ClaimReviewVerdict = 'SUPPORTED' | 'CONTRADICTED' | 'INSUFFICIENT' | 'PENDING_REVIEW';
type ClaimReview = {
  claimId: string;
  claim: string;
  evidenceIds: string[];
  verdict: ClaimReviewVerdict;
  reasons: string[];
  reviewer: { kind: 'deterministic' | 'external'; version: string };
};
```

确定性门禁先检查 scope、snapshot、时间窗、币种、单位、evidenceId 和值重算；未通过时不调用外部 Reviewer。外部 Reviewer 只给审查意见，超时或不可用记 PENDING_REVIEW，绝不提升 proposal 权限。没有外部 Reviewer 时只能声称完成了确定性 claim-evidence 一致性检查。

## 10. 数据表、迁移与事务边界

### 10.1 新表

PostgreSQL 与 SQLite 合同至少覆盖：

- `commerce_schema_migrations(version, checksum, applied_at)`；同版本不同 checksum 拒绝启动。
- `commerce_imports(import_id, tenant_id, shop_id, source_type, source_id, status, manifest_json, counts_json, created_at, updated_at)`。
- `commerce_record_versions(record_version_id, tenant_id, shop_id, kind, source_record_id, version, content_hash, business_time, payload_json, import_id, ingested_at)`，唯一键 `(tenant_id, shop_id, kind, source_record_id, version)` 及 `(tenant_id, shop_id, kind, source_record_id, content_hash)`。
- `commerce_quarantine(quarantine_id, import_id, tenant_id, shop_id, kind, row_number, code, message, raw_json, created_at)`。
- `commerce_snapshots(snapshot_id, tenant_id, shop_id, import_id, as_of, completeness_json, metric_definition_version, created_at)`。
- `commerce_snapshot_records(snapshot_id, record_version_id, tenant_id, shop_id)`，scope 与外键一致。
- `commerce_report_reviews(review_id, report_id, tenant_id, shop_id, snapshot_id, status, reviews_json, reviewer_json, created_at)`。

所有 tenant/shop 查询都应有复合索引；外键不允许只关联无 scope 的主键。payload 用 JSONB（PostgreSQL）/TEXT JSON（SQLite）；金额继续保存安全整数，不使用 float。

### 10.2 事务与幂等

单批 apply 的事务顺序：锁定/创建 import -> 写 record versions/quarantine -> 生成 snapshot membership -> 写完整性与计数 -> 更新 import 终态 -> 提交。snapshotId 由 manifest hash 与最终 recordVersionIds 的有序 hash 派生；同一 manifest 和同一数据库状态重试返回同一逻辑结果。事务失败后不得留下 APPLIED/PARTIAL 或游标推进。

PostgreSQL migration 只做 expand，不 drop 旧表。migration runner 对每个文件按版本排序、校验 SHA-256、在 advisory lock 下单事务执行；失败保留原版本。没有明确测试 URL 时 `commerce:test:postgres` 非零退出并报告外部条件，不能打印 skipped success。

## 12. 编码批次与逐批验证

### B00：基线和 ADR

### B02：文件导入和事务仓库

输入：manifest 与文件。输出：dry-run 结果、apply 批次、版本、quarantine、snapshot。断言：重复导入不翻倍、变更同 ID 生成 revision、行级坏数据进入隔离、摘要/路径/scope 错误整批拒绝、事务注入失败无可见 snapshot。完成条件：JSON/JSONL/CSV 和五类数据测试通过。

输入：可信 scope、固定 snapshot、五类 query。输出：兼容 01 的 ToolEnvelope 与治理证据。断言：跨 tenant/shop、非 snapshot 记录、窗口外记录均不可见；同 Run 查询固定 snapshot；来源、记录 ID、定义版本可追踪；旧 Fixture 合同不回归。完成条件：Adapter 合同和反例通过。

### B04：HTTP 测试源

输入：受控分页 endpoint。输出：规范化 page/cursor 导入。断言：429 遵守 Retry-After 与总重试上限；重复/乱序不重复记账；游标失效明确失败或从绑定 snapshot 重启；AbortSignal 中止；跨页 snapshot token 变化拒绝。完成条件：本地独立 HTTP server 集成测试通过。
