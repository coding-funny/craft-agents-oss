# 07：部署运维与试运行验收链路

状态：CODE_READY；PILOT_BLOCKED_EXTERNAL。产物类型：Runtime supporting / Eval / Delivery。目标是将前六条链路交付为可部署、可观测、可恢复、可评价运行边界的版本。

## 1. 必读输入与进入条件

读 [入口](./README.md)、[共享契约](./00-总体设计与共享契约.md)、01—06 的验收摘要、[执行记录](./EXECUTION-LOG.md)。

源码与环境必读：`Dockerfile.server`、`package.json`、`packages/commerce-agent/package.json`，02 新增的数据库/导入/迁移，03 认证配置，04 Worker 与测试平台，05 release-policy，06 UI 与事件部署要求。

最终发布依赖前六条必需门槛。可以提前完成镜像/CI/观测配置，但不得因部署能启动而跳过真实模型与权限验收。

## 2. 业务结果与范围

提供一套 staging 部署和故障/恢复演练。受控试运行用获授权数据和明确使用者进行，建议观察 7 天；没有这些条件时只完成工程发布验收，试运行单列 BLOCKED_EXTERNAL。

目标为限定规模下可验证的运行能力，不声称无限扩展或未经观察的全年可用性。真实平台写入默认关闭，开启需要该平台实际适配、能力测试和授权，不属于自动部署附带动作。

## 3. 拟改动位置

| 路径 | 职责 |
| --- | --- |
| `deploy/commerce/` | 镜像、Compose、配置模板、身份/代理、观测配置 |
| `packages/commerce-agent/src/observability/` | Trace、指标、脱敏日志 |
| `packages/commerce-agent/src/health/` | readiness、liveness、依赖和 Worker 状态 |
| `packages/commerce-agent/scripts/` | 预检、迁移、备份验证、负载及 soak 驱动 |
| `.github/workflows/commerce-ci.yml`（拟新增） | 仓库使用 GitHub Actions 时的 CI；当前未发现 .github 目录 |
| `packages/commerce-agent/docs/operations/` | Runbook、SLO、发布/恢复/试运行记录 |

若远端实际使用其他 CI，采用对应系统并记录决定，不仅生成无人执行的 workflow。当前规划不执行部署或创建外部资源。

## 4. 执行任务

### 07.1：可复现部署

- [ ] 明确 API/UI、调查 Worker、执行 Worker、PostgreSQL、测试平台、身份提供方及观测后端的配置和网络边界。
- [ ] 审查现有 Dockerfile 的依赖、Bun 运行环境与 shared 后端子进程需求，复用可用部分；锁定依赖，非 root 运行，优雅退出。
- [ ] 提供 fixture/sandbox/pilot 配置模板和启动前 preflight，缺失密钥、错误模式、无审批身份等配置 fail fast。
- [ ] 密钥从受控环境/secret 文件注入，不打包进镜像、日志或前端 bundle；平台写密钥只给执行进程。
- [ ] 本地默认绑定 loopback；外部试运行配置 HTTPS、回调地址、CORS、CSRF、事件代理超时和上传限制。
- [ ] readiness 与 liveness 分离：依赖暂时失败不能造成无意义重启风暴；Worker 暴露心跳/租约而不是只检查进程存在。

### 07.2：端到端观测

- [ ] 用 OpenTelemetry 关联 API、模型、工具、校验、审批、队列、执行和对账。采用 task/run/proposal/request 对应关系，记录配置与数据版本。
- [ ] 指标至少包括任务结果、队列等待、执行时延、工具错误/重试、token/费用、租约接管、UNKNOWN 数量/停留时间、审批拒绝原因、数据新鲜度。
- [ ] taskId 等高基数字段放 Trace/日志，不直接作为 Prometheus 风格指标 label；租户指标控制基数并避免泄漏。
- [ ] 阈值告警覆盖 Worker 无心跳、队列滞留、UNKNOWN 超时、持续模型/平台失败、预算耗尽、备份失败；用注入测试验证触发与恢复。
- [ ] 定义审计、调试日志、原始模型记录的访问、保留和删除策略；敏感数据删除时记录证据失效，不能继续假装报告可完整复现。

### 07.3：CI 与发布

- [ ] PR/default CI 运行 commerce 类型检查、单元/合同、PostgreSQL 集成、权限、执行故障核心集、评测数据与评分器、UI 构建及关键浏览器测试。
- [ ] 有预算的发布/定期 job 运行真模型评测和冻结门禁；无需每个小提交执行全量付费回放。
- [ ] 运行依赖漏洞与许可证检查，记录结果与实际影响；继承项目许可证和必要 NOTICE 保留，产品命名独立不等于移除来源义务。
- [ ] 发布 manifest 绑定 commit、镜像、Schema、model/prompt/tool/policy/eval 版本。以显式结果决定发布，不以缺凭证 job skipped 当成功。
- [ ] 演练模型配置、应用版本回退；Schema 采用兼容迁移，破坏性操作另行明确目标，不能自动删用户数据。

### 07.4：负载与恢复实验

- [ ] 分开测三类负载：不调用模型的 API/DB、受控延迟模型的 Worker 调度、真实模型端到端。报告不能混用三者延迟。
- [ ] 起始实验配置建议为 2 tenant、每 tenant 2 shop、10 万条生成销售记录、2 个 Worker、10 个并发任务；真实模型并发另设为 1—2 并受预算限制。记录机器、索引、冷/热缓存和平台限额。
- [ ] 起始容量测试点：只读 API 20 req/s 持续 10 分钟，候选目标 P95 ≤ 500ms、错误率 < 1%；只作为待校准的实验目标，不是已测结果。
- [ ] 通过 dev/staging 基线固定延迟、吞吐、成本和恢复门槛，再执行最终验收；调整门槛需事先记录原因，不能测完失败后静默放宽。
- [ ] 用受控模型/生成任务执行至少 24 小时 soak，期间按计划重启 Worker、限流/断开测试平台、重启数据库；实时模型另做有限样本以控制费用。保留每次检查与实际持续时长。
- [ ] 验证备份可用而非仅生成备份文件：恢复到新实例，核对记录/证据哈希、审批/请求台账，运行只读一致性检查和恢复演练。
- [ ] 起始设计目标 RPO ≤ 24 小时、RTO ≤ 30 分钟；依据备份方案和实际恢复测量验收。恢复后先核实远端动作再开执行 Worker，防止较旧备份导致重复写入。

### 07.5：受控试运行与交付

- [ ] 明确试运行商家/使用者、数据授权、部署位置、允许动作、模型预算、运行日期和联系人；缺失条件只阻塞相应外部步骤。
- [ ] 先只读 shadow 模式，比较人工判断与 Agent 报告；经实际授权后才扩大到受控动作，测试平台执行可以一直保留。
- [ ] 建议观察 7 天，记录任务数、结果、反馈、成本、故障、恢复和实际覆盖的交易/异常范围；没有异常发生不等于证明异常处理可靠。
- [ ] 完成操作手册、5 分钟架构说明、10 分钟包含失败路径的 Demo、决策记录和源码/测试/Trace 导航。
- [ ] 按真实验收更新架构和项目描述；可用性、商家数、模型质量、业务收益仅采用本轮实际证据，未观察到的留空。

## 5. 验证与命令

拟新增命令和文件，实施后才能执行：

```bash
bun run commerce:preflight -- --config <staging-config.json>
docker compose -f deploy/commerce/compose.yaml up -d
bun run commerce:test:deploy
bun run commerce:loadtest -- --config <load-config.json>
bun run commerce:soak -- --config <soak-config.json>
bun run commerce:backup:verify -- --config <restore-test-config.json>
bun run commerce:release:check -- --manifest <release-manifest.json>
```

preflight 不输出 secret 值。负载与恢复命令必须验证目标是专用环境，不能默认指向生产库。长时实验通过持久 runner 输出进度与结果，不要求 AI 对话阻塞等待一天；只有达到实际时长后才记为通过。

## 6. 完成门槛与交付证据

- [ ] 从干净环境按手册部署成功，依赖与配置明确，关键业务路径通过。
- [ ] 01—06 门槛及发布门禁通过，无未解决的权限越界、重复副作用或数据损坏。
- [ ] Trace 可从任务定位模型/工具/动作，告警触发与恢复经过测试。
- [ ] 压测、24 小时 soak、备份恢复和版本回退有实际原始结果；未测完不能提前标 VERIFIED。
- [ ] 提供可部署版本、真实模型评测报告、故障恢复记录、性能成本报告和演示五项工程交付。
- [ ] 试运行独立记录 COMPLETE/BLOCKED_EXTERNAL；工程验收通过不自动表示真实业务生产上线。

## 7. 回退、交接与验收记录

回退手册明确：停止新写任务→确认/记录在途请求→切换兼容应用和配置→验证身份/数据/幂等台账→逐步恢复处理。UNKNOWN 不因回退而清除。数据库恢复先在隔离实例验证，再决定切换；删除/覆盖目标需要明确授权。

最终交接是工程包和已知限制清单，不自动执行公网发布、真实商家写操作或简历投递。后续扩容、平台适配或新场景作为新计划，沿用同样的验收循环。

验收记录：本地工程实现已完成，实际部署/运行时长/负载曲线/RTO/费用仍待专用环境填写。当前 API/Worker 运行时仅接入 SQLite，因此 pilot preflight 会以 `PILOT_STORAGE_ADAPTER` 阻断；存在 PostgreSQL migration 不等于完成运行时切换。

## 8. 本轮实际接口与状态

| 输入 | 输出 | 状态语义 |
| --- | --- | --- |
| deployment JSON + 环境变量引用 | PreflightResult | PASS / BLOCKED / FAIL，不输出 secret 值 |
| `GET /health/live` | 进程存活与 uptime | 依赖故障不触发 liveness 失败 |
| `GET /health/ready` | DB、Schema、必需 Worker 心跳 | READY / 503 NOT_READY |
| `GET /metrics` | Prometheus text | 仅低基数聚合，不含 tenant/task label |
| SQLite 源库 + 非生产确认 | 独立 backup、integrity、关键表 digest | 不覆盖源库，不接受 pilot/production |
| release manifest | 发布决策与原因码 | 结构错误/测试失败 FAIL；缺外部证据 BLOCKED |

## 9. 实际修改文件

- `deploy/commerce/`：API/UI 镜像、loopback Compose、同源反代、sandbox/pilot 配置和 release manifest 模板。
- `src/config/deployment.ts`、`src/health/`、`src/observability/`、`src/operations/`、`src/release/`：预检、心跳、健康、指标、脱敏、恢复校验和发布门禁。
- `scripts/`：preflight、loadtest、backup verify、release check；负载工具只允许 loopback fixture/sandbox。
- `tests/deployment/`、`.github/workflows/commerce-ci.yml`、`docs/operations/`：合同测试、CI 与交接材料。

## 10. 测试断言与完成条件

- Sandbox 完整配置 PASS；内联 secret FAIL；pilot 因未接 PostgreSQL runtime 明确 BLOCKED。
- liveness 始终只表达进程；readiness 在缺 Worker 心跳时失败，新鲜心跳后恢复。
- 指标不暴露 tenant/task 高基数标签；凭证键和 Bearer 内容脱敏。
- 备份必须通过 `PRAGMA integrity_check`，关键 job/feedback/execution/approval 表行数和 SHA-256 一致。
- pilot manifest 必须包含 live 评测及人工复核、PostgreSQL、浏览器 E2E、恢复和至少 24h soak。
- 本地代码条件全部通过后状态为 CODE_READY；镜像实际构建、OTLP/告警、Worker 进程、PostgreSQL runtime 和真实环境证据齐全后才可改为 VERIFIED。
