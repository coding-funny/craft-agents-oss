## 2. 业务结果与范围

运营人员只能查看获授权店铺、发起调查和提交提案；审批人可在权限与额度内批准/拒绝；执行由专用服务身份完成。管理员负责授权配置，不能通过普通报告编辑绕过执行审计。

首轮采用一个受维护的身份验证方案。默认评估 OIDC Authorization Code + PKCE 与服务端会话，开发/测试使用本地身份提供方；若已有宿主认证能可靠提供稳定主体，可复用其认证，但仍新增业务授权映射。用 ADR 固定选择，不同时实现多套登录或自建密码体系。

业务 API 保持独立模块，默认复用现有 server 的挂载能力；如无法证明其公开入口的会话隔离，提供独立 commerce API 启动入口，记录集成决定。

### 8.2 固定实现选择

1. 身份方案采用 OIDC Authorization Code + PKCE，`jose` 校验 ID Token 签名、issuer、audience、expiry 和 nonce。测试使用本地签名 IdP 完整走 authorize/token/JWKS，不用 mocked Principal 替代认证验收。
2. 浏览器使用服务端 opaque session；数据库只存 session token 的 SHA-256。Cookie 固定 `HttpOnly; Secure; SameSite=Strict; Path=/`，写接口同时要求 allowlisted Origin 和 session 绑定 CSRF token。
3. OIDC token 只证明外部 subject。tenant、roles、shop grants 每次由服务端 Membership Repository 解析；撤销授权后旧 session 立即失效。
4. 首版角色为 `OPERATOR`、`APPROVER`、`ADMIN`、`EXECUTOR`、`AUDITOR`。权限由版本化 policy 映射，不接受 token/body 自报角色。
5. API 作为 `packages/commerce-agent` 独立 Bun HTTP 入口；本链路不改全局 server 路由。06 可按稳定 OpenAPI/handler 挂载。
6. Proposal v2 哈希绑定 tenant/shop/requestedBy、动作、参数、targetVersion、证据 IDs、snapshotId、reviewStatus、policyVersion、有效期和报告；任何字段变化都产生新哈希/提案。
7. 默认禁止自审。审批必须提交页面看到的 proposalHash；角色、shop grant、动作/额度、授权状态、policy version、证据 freshness/review 状态在批准时检查，并在执行前重查。
8. 模型仍可创建“待审批提案”，但不能批准、拒绝或执行。MCP 子进程不接收 OIDC session、CSRF、审批身份或平台写凭据。
9. SQLite 用于可执行合同和本地 OIDC/API 集成；PostgreSQL 是生产目标。没有真库时不能标记 `RLS_VERIFIED`。

## 9. 输入、输出、接口与状态

### 9.1 身份与授权

```ts
type CommerceRole = 'OPERATOR' | 'APPROVER' | 'ADMIN' | 'EXECUTOR' | 'AUDITOR';
type CommercePermission =
  | 'task:create' | 'task:read' | 'report:read' | 'evidence:read'
  | 'proposal:create' | 'proposal:read' | 'proposal:approve' | 'proposal:reject'
  | 'proposal:execute' | 'audit:read' | 'access:manage';

type AuthenticatedPrincipal = {
  actorId: string;
  subject: string;
  tenantId: string;
  roles: CommerceRole[];
  permissions: CommercePermission[];
  allowedShopIds: string[];
  authSource: 'oidc-session' | 'service-identity' | 'local-test';
  sessionId?: string;
  membershipVersion: number;
};
```

`AuthenticatedPrincipal` 只能由 auth service 构造。HTTP body/query/header 中出现 actorId、tenantId、roles、permissions 或 allowedShopIds 时严格 Schema 拒绝。适配到 01 时仅产生 `investigate/read_evidence/read_report` 三项已有权限。

### 9.2 OIDC flow 与 session

```ts
type OidcFlow = {
  stateHash: string;
  nonceHash: string;
  codeVerifier: string;
  tenantHint?: string;
  expiresAt: string;
  consumedAt?: string;
};

type CommerceSession = {
  sessionId: string;
  tokenHash: string;
  csrfHash: string;
  subject: string;
  tenantId: string;
  membershipVersion: number;
  createdAt: string;
  expiresAt: string;
  revokedAt?: string;
};
```

状态必须一次性：`OIDC_FLOW_CREATED -> CONSUMED|EXPIRED`；session 为 `ACTIVE -> REVOKED|EXPIRED`。state/code 重放失败。token endpoint 使用 PKCE verifier；ID token nonce 与 flow 绑定。未知 subject、停用 membership、tenantHint 不匹配不创建 session。

### 9.3 Membership 与 shop grants

```ts
type Membership = {
  actorId: string;
  subject: string;
  tenantId: string;
  roles: CommerceRole[];
  status: 'ACTIVE' | 'REVOKED';
  version: number;
};
type ShopGrant = { actorId: string; tenantId: string; shopId: string; status: 'ACTIVE' | 'REVOKED' };
```

同一 subject 可属于多个 tenant；登录 flow 必须明确 tenantHint 或只有一个 active membership。Session 保存 membershipVersion；解析时版本不一致即失效。ADMIN 也不自动跨 tenant，只能管理当前 tenant。

### 9.4 API envelope 与错误

成功：`{ ok: true, data, traceId }`。失败：`{ ok: false, error: { code, message }, traceId }`。生产错误不返回 SQL、token、跨 scope ID、stack 或文件路径。

核心路由：

| Method/path | 权限 | 输入/输出 |
| --- | --- | --- |
| `GET /api/v1/auth/start` | public | tenant query；302 authorization URL |
| `GET /api/v1/auth/callback` | public + state/code | Set-Cookie；csrfToken/principal summary |
| `POST /api/v1/auth/logout` | session + CSRF | 撤销当前 session |
| `GET /api/v1/me` | session | 当前 roles/shops |
| `POST /api/v1/tasks` | task:create | InvestigationInput；幂等创建 task |
| `GET /api/v1/tasks/:id` | task:read | scoped task；越权与不存在均 404 |
| `GET /api/v1/tasks/:id/events` | task:read | sequence cursor/limit 稳定分页 |
| `GET /api/v1/reports/:id` | report:read | tenant/shop scoped report |
| `GET /api/v1/evidence/:id` | evidence:read | governed evidence；legacy evidence 生产拒绝 |
| `GET /api/v1/proposals/:id` | proposal:read | scoped immutable proposal |
| `POST /api/v1/proposals/:id/approve` | proposal:approve | confirmHash/reason |
| `POST /api/v1/proposals/:id/reject` | proposal:reject | confirmHash/reason |

任务创建要求 `Idempotency-Key`；键域为 tenant+actor+operation+key。相同 payload 返回原 response；不同 payload 返回 409。事件 cursor 是只增 sequence，不接受任意 SQL。

### 9.5 Proposal v2 与策略决策

```ts
type GovernedProposalContent = {
  tenantId: string;
  shopId: string;
  requestedBy: string;
  reportId: string;
  recommendationId: string;
  evidenceIds: string[];
  snapshotId: string;
  reviewStatus: 'REVIEWED' | 'PENDING_REVIEW' | 'REJECTED' | 'LEGACY_DEMO';
  actionType: ActionType;
  targetId: string;
  targetVersion: number;
  parameters: Record<string, string | number | boolean>;
  riskLevel: 'LOW' | 'MEDIUM' | 'HIGH';
  policyVersion: string;
  createdAt: string;
  expiresAt: string;
};
```

Policy 成功结果为 `ALLOW | ALLOW_LEGACY_TEST`，拒绝通过稳定 `DENY_*` reason code 表达。至少检查：permission、shop grant、self-approval、proposalHash、expiry、policyVersion、金额限制、targetVersion 和 reviewStatus。审批记录同时保存 principal actor/subject/session、proposalHash、policyVersion 和 reason。

执行身份必须为 `service-identity + proposal:execute`；执行前读取最新 membership/grant/policy，确认批准记录仍绑定当前 proposalHash/policyVersion。03 只加执行前治理门禁，崩溃恢复仍由 04 完成。

- `commerce_authz_audit(event_id, trace_id, tenant_id, actor_id, subject, shop_id, action, decision, reason_code, created_at)`。

PostgreSQL 对 tenant 表启用并 `FORCE ROW LEVEL SECURITY`。policy 使用 `current_setting('app.tenant_id', true)`；Repository 每个事务通过 `set_config(..., true)` 设置 tenant/actor，结束后不能残留。迁移角色和应用角色分离作为部署要求，测试 URL 缺失时 RLS 真验收非零失败。

Session token、authorization code、ID/access token、PKCE verifier、CSRF 原值不进入日志或审计。审计 details 使用 allowlist 字段。普通应用代码没有 delete/update authz audit 的接口；这不是防数据库管理员篡改证明。

输入：tenant/shop scope。输出：roles/permissions/principal、membership/grant/session/flow Repository、SQLite Schema、PG migration。断言：角色不能自报；membership version/revoke 生效；同 subject 多 tenant 需明确选择；所有资源带 scope。完成：类型与 repository 合同通过。

### B02：OIDC Code+PKCE 与安全 session

输入：issuer/JWKS/authorization/token endpoints、client/redirect。输出：start/callback/logout、opaque cookie/CSRF。断言：state/nonce/PKCE/issuer/audience/expiry/签名错误、code/state 重放、session token 明文落库均失败。完成：本地签名 IdP 的真实 HTTP 流通过；外部 IdP 另标。

### B03：授权 middleware 与业务 API

输入：Cookie、Origin、CSRF、Schema。输出：me/task/event/report/evidence/proposal/approve/reject handlers。断言：无认证 401；权限或跨 scope 404/403 按契约；body actor/tenant 拒绝；CORS/CSRF；trace/error 脱敏；幂等冲突 409。完成：两个 tenant、同 tenant 两 shop API 矩阵通过。

### B04：Proposal v2 与审批策略

输入：报告/evidence/snapshot/review/principal/policy。输出：不可变 Proposal v2 与 policy decision。断言：自审、错误 hash、无 grant、无 role、超额度、旧 policy、过期/PENDING_REVIEW/STALE 均拒绝；approve/reject 竞态只一方成功。完成：审计记录含发起/审批主体和 reason code。

### B05：执行前重验与凭据隔离

输入：已批准提案、执行 service principal、最新授权/策略。输出：允许执行或 fail-closed。断言：批准后撤销 membership/grant、policy 变化、参数/targetVersion 变化、过期均不执行；模型 MCP 环境无 session/CSRF/写凭据。完成：原 mock idempotency/reconciliation 回归不下降。

### B06：CLI 降权、文档和完整回归

### B07：PostgreSQL RLS 与外部 OIDC 验收
