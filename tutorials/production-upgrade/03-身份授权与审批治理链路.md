# 03：身份授权与审批治理链路

状态：PLANNED。产物类型：Workflow / Harness supporting。目标是将操作员身份、店铺作用域和人审权限从本地约定升级为可测试的服务端边界。

## 1. 必读输入与进入条件

读 [入口](./README.md)、[共享契约](./00-总体设计与共享契约.md)、[02](./02-数据接入与证据治理链路.md)及其交接结果。

源码必读：`packages/commerce-agent/src/approvals/`、`src/cli/approve.ts`、`reject.ts`、`execute.ts`、`src/execution/execution-service.ts`、`src/mcp/server.ts`、`src/tools/get-evidence.ts`、`get-proposal.ts`；审查 `packages/server/src/index.ts` 与现有服务认证入口。

02 的 PostgreSQL Repository 和作用域合同测试必须通过；真实数据外部验收可以独立保留。01 的模型运行边界已经能够限制工具集合。

## 2. 业务结果与范围

运营人员只能查看获授权店铺、发起调查和提交提案；审批人可在权限与额度内批准/拒绝；执行由专用服务身份完成。管理员负责授权配置，不能通过普通报告编辑绕过执行审计。

首轮采用一个受维护的身份验证方案。默认评估 OIDC Authorization Code + PKCE 与服务端会话，开发/测试使用本地身份提供方；若已有宿主认证能可靠提供稳定主体，可复用其认证，但仍新增业务授权映射。用 ADR 固定选择，不同时实现多套登录或自建密码体系。

业务 API 保持独立模块，默认复用现有 server 的挂载能力；如无法证明其公开入口的会话隔离，提供独立 commerce API 启动入口，记录集成决定。

## 4. 执行任务

### 03.1：身份接入与主体传播

- [ ] 定义 actor、tenant membership、shop access、role permissions，数据库保存可撤销授权关系。
- [ ] 验证登录签名、issuer、audience、expiry、state/nonce；浏览器会话设置 HttpOnly/Secure/SameSite，写接口处理 CSRF；CORS 使用明确允许来源。
- [ ] 请求作用域从服务端身份映射产生，模型/请求 body 的 actor/tenant 字段不可覆盖可信上下文。
- [ ] Worker 服务身份与操作员身份分离，审计同时记录发起人、审批人、实际执行主体。
- [ ] fixture 模式保留固定本地身份；部署模式拒绝 demo actor、自报 header、autoApprove 等开发绕过选项。

### 03.2：业务 API 与作用域

- [ ] 实现 `/commerce/tasks` 创建/读取、任务事件、报告、Evidence、Proposal 查询及 approve/reject API；发布稳定请求/响应 Schema。
- [ ] 创建任务带幂等请求键，键域包含 tenant、actor、operation；相同键不同 payload 返回冲突，不复用错误任务。
- [ ] tenant/shop 验证覆盖列表、详情、ID 直读、搜索、导出、Trace 和下载；跨域对象返回不泄露存在性的错误。
- [ ] 列表使用稳定分页，错误响应含 traceId 但不含密钥、SQL、跨租户元数据。
- [ ] RLS 作为补充防护：应用角色非表所有者且无 BYPASSRLS，事务内设置租户上下文并避免连接池串租户；迁移角色独立。

### 03.3：审批策略与不可变提案

- [ ] 批准和拒绝仅由可信 PrincipalContext 调用，弃用生产路径中的任意 actor 字符串。
- [ ] 提案哈希绑定动作参数、目标版本、证据快照、策略版本、有效期与报告；修改产生新提案，旧审批不能复用。
- [ ] 角色策略限制店铺、动作类型、额度/调整比例；默认发起人与审批人分离，demo 演示双角色使用不同账号。
- [ ] 确认页面/API 显式提交所看到的 proposalHash，展示与批准版本一致；批准前执行证据新鲜度和复核状态检查。
- [ ] 执行前重复验证批准状态、当前撤销情况、有效期和目标版本；策略变化采用 fail-closed，要求重新审批，不默默沿用旧额度。
- [ ] 审批/拒绝竞态通过事务状态条件更新解决，事件与状态同事务持久化。

### 03.4：工具和凭据隔离

- [ ] 模型工具只开放作用域查询、报告校验、提案；列工具和真正执行端均做限制。
- [ ] 模型 Worker 不接收平台写密钥与审批凭据。即使共享物理机器，也不开放任意文件/数据库/Shell 绕过路径。
- [ ] 外部商品名、描述、导入内容作为不可信数据；注入“替我批准/查询另一店铺”不能改变 PrincipalContext。
- [ ] 数据库审计设置应用不可修改历史事件的权限，记录关键授权/审批操作；不把同库普通哈希宣称为防管理员篡改证明。

## 5. 验证矩阵

| 场景 | 验收结果 |
| --- | --- |
| tenant A 读取 B 的报告、Evidence、Trace、列表和导出 | 拒绝，无内容/存在性泄露 |
| 同 tenant 不同店铺，伪造 shop/actor | 拒绝，以真实会员权限为准 |
| 运营审批、发起人自审、过期会话 | 拒绝并留审计 |
| approve/reject 并发、重复请求 | 一个合法状态结果，无多次授权效果 |
| 审批后参数/策略/权限/目标版本变化 | 不执行，标明需刷新或重新审批 |
| 连接池交替服务两个租户 | 不残留上一租户上下文 |
| 商品描述 Prompt Injection | 无越权工具、无授权扩张 |
| 无合法凭据直接调用写 API/旧 CLI | 生产模式拒绝 |

拟新增命令：

```bash
bun run commerce:test:auth
bun run commerce:test:api
bun run commerce:test:approval-policy
```

需要真实 PostgreSQL 和本地身份测试环境。还应运行 02 Repository 测试、电商全回归；若修改宿主，运行其 API/启动回归。

## 6. 完成门槛与交付证据
