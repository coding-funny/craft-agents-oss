## 实现步骤

### E15：补齐宿主恢复与端到端完成判定

1. 覆盖会话重启、MCP 重连和进行中任务恢复。
2. Demo Runner 必须等待以下终态之一：

   - 报告 Artifact 已持久化且通过校验；
   - Proposal 进入明确终态；
   - 执行成功、失败或 UNKNOWN；
   - 明确超时。

3. 不以消息发送已接受、模型首个 token 或工具开始调用作为完成信号。
4. Runner 输出最终 `session_id`、`report_id`、`proposal_id`、`trace_id` 和状态。
5. 恢复后重复运行不得产生重复 Proposal 或重复副作用。

### E16：建立评测集、基线与消融

目标数据集为 24 条左右，建议：

- 16 条开发集；
- 8 条保留集；
- 覆盖库存、促销、广告、退款、时间窗、缺失数据、冲突证据和审批安全。

如果暂时无法达到 24 条，必须真实记录当前数量，不得把少量手工 Demo 宣称为完整评测。

评分至少包含：

- Tool Selection Accuracy；
- Argument Correctness；
- Evidence Coverage；
- Numeric Correctness；
- Root-cause Support；
- Unsupported Claim Rate；
- Report Completion Rate；
- Approval Safety；
- Idempotency Success；
- Recovery Success；
- 端到端延迟。

建立至少两组对照：

1. 单轮 Prompt + 全量数据；
2. 工具化多步诊断，但关闭部分机制。

消融至少覆盖：

- 无 Skill；
- 无 Evidence Gate；
- 无重试预算；
- 无审批哈希校验；
- 无幂等保护；
- 无恢复机制。

结果报告必须区分确定性脚本评分与人工评分，并给出样本数、失败样例和局限。

### E17：故障注入、一键 Demo 与面试材料

故障注入至少覆盖：

- MCP 超时；
- 429 限流；
- 非法 schema；
- 数据源缺失；
- 证据冲突；
- 报告持久化失败；
- 审批过期或 Proposal 被篡改；
- 并发执行；
- 执行成功但响应丢失；
- 会话中断与恢复。

一键 Demo 至少串起：

1. 安装或检查 Source；
2. 启动电商 MCP；
3. 发起销量下滑诊断；
4. 生成并校验报告；
5. 从报告创建 Proposal；
6. 人工批准；
7. Mock 执行；
8. 重复执行验证幂等；
9. 输出 Trace 和审计摘要。

面试材料包括：

- 5 分钟架构讲解；
- 10 分钟 Demo 脚本；
- 关键技术决策与替代方案；
- 失败案例和修复过程；
- 大厂面试常见追问；
- 每条简历 bullet 对应的代码、测试、Trace 或评测证据。

## 强制测试与实验

- 会话中断后恢复并完成报告；
- MCP 重连后 Trace 连续或具备明确父子关系；
- 端到端 Runner 正确等待终态；
- 24 条目标评测或如实记录的阶段性评测；
- 两组基线和至少六项消融；
- 十类故障注入全部产出结构化结果；
- 一键 Demo 在干净环境重复运行至少两次；
- 第二次 Demo 不产生重复副作用；
- 简历证据映射表不存在“计划中”内容冒充“已实现”。

## 完成门槛

- 端到端 Demo 能从诊断稳定走到审批与 Mock 执行；
- 会话重启、MCP 重连和响应丢失均有可复现恢复结果；
- 评测报告包含样本、指标、基线、消融、失败案例和局限；
- 一键 Demo 可重复运行，且第二次运行不重复产生副作用；
- 架构、决策、演示、面试问答和简历证据映射齐全；
- 所有简历数字均来自真实命令输出，且保留原始结果；
- `progress.md` 最终状态标记为完成，并列出仍未实现的生产化能力。

## 禁止事项

- 不为了提高分数把保留集答案写入 Prompt；
- 不只展示成功样例；
- 不把 Fixture/Mock 指标描述成线上生产收益；
- 不宣称已经支持真实商家写操作；
- 不把模型主观评分作为唯一质量指标；
- 不隐藏失败注入和局限；
- 不把未完成能力写进简历完成项。

## 最终交付

- 可运行代码与完整测试；
- 结构化报告、Proposal、审批、Mock 执行和审计证据；
- 评测数据集、基线、消融和故障注入报告；
- 一键 Demo；
- 架构与决策文档；
- 面试 Q&A；
- 可直接用于简历的、逐条有证据支撑的项目描述。
