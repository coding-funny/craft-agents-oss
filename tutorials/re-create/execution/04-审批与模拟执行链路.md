# 链路 4：审批与模拟执行

## AI 任务

把报告中的高风险建议转换为不可篡改的 Proposal，通过模型外的人工审批入口完成批准或拒绝，再由 Mock Executor 执行。实现持久化状态机、审计日志、幂等、并发控制和未知结果核对。

## 必读输入

- [链路 3：诊断与报告](./03-诊断与报告链路.md)
- `tutorials/02-电商数据工具与审批契约.md` 中审批状态、幂等和审计要求
- 仓库现有权限与工具暴露机制
- `packages/commerce-agent/demo/progress.md`

## 进入条件

- 结构化报告可稳定生成并通过质量门禁；
- 报告中建议动作可关联 Evidence；
- 只读工具权限与后续写操作权限明确分离。

## 允许改动范围

- `packages/commerce-agent/**`
- 电商 Source 中与 Proposal 查询相关的只读工具声明
- 独立的人工审批 CLI 或本地 UI
- 不接入真实平台写接口

## 实现步骤

### E11：实现 Proposal 与持久化审批状态机

1. 使用 SQLite 持久化 Proposal、Approval、Execution Attempt 和 Audit Event。
2. Proposal 至少包含：

   - `proposal_id`
   - 来源 `report_id`、`trace_id`、`evidence_ids`
   - 动作类型、目标对象、参数
   - 风险等级、预计影响和回滚说明
   - 内容摘要哈希
   - 创建时间、过期时间和当前状态

3. 状态机：

```text
DRAFT -> PENDING_APPROVAL -> APPROVED -> EXECUTING -> SUCCEEDED
                           \-> REJECTED
                           \-> EXPIRED
                                      EXECUTING -> FAILED
                                      EXECUTING -> UNKNOWN
```

4. 状态迁移必须使用事务和条件更新，拒绝非法跳转。
5. Proposal 内容变化后原审批失效，必须重新提交。

### E12：实现模型外人工审批入口

1. 模型只能创建和查询 Proposal，不能调用批准、拒绝和执行接口。
2. 人工 CLI 或本地 UI 展示：

   - 完整动作与参数；
   - 证据和来源报告；
   - 风险说明；
   - 幂等键；
   - 过期时间。

3. 审批人输入独立确认，记录 `actor`、时间、理由和内容哈希。
4. 未审批、拒绝、过期、被篡改的 Proposal 均不可执行。

### E13：实现 Mock Executor 与审计

1. Mock 平台状态与分析 Fixture 分开存储，避免执行结果污染原始证据。
2. 支持有限动作，例如：

   - 调整 Mock 广告预算；
   - 暂停 Mock 广告活动；
   - 创建 Mock 补货任务；
   - 创建 Mock 促销调整工单。

3. 执行前再次校验 Proposal 状态、哈希、有效期和权限。
4. 所有尝试写审计日志，包括失败和拒绝。
5. 执行后保存结构化结果、前后状态和可选补偿动作。

### E14：实现幂等、并发与 UNKNOWN 核对

1. 幂等键至少由 `proposal_id + action_type + target_id + version` 组成。
2. 数据库为幂等键建立唯一约束。
3. 并发执行时只允许一个调用获得执行权。
4. 远端已成功但本地响应丢失时，状态设为 `UNKNOWN`，不得自动再次写入。
5. `reconcile` 根据 Mock 平台状态和外部操作 ID 核对：

   - 已生效：标记 `SUCCEEDED`；
   - 未生效：标记 `FAILED` 或允许人工重试；
   - 无法判断：保留 `UNKNOWN` 并告警。

## 强制测试

- 合法与非法状态迁移；
- Proposal 篡改后审批失效；
- 未审批、拒绝、过期均无法执行；
- 模型工具列表中没有 approve/reject/execute；
- 两个并发执行请求只有一个产生副作用；
- 相同幂等键重复调用返回首次结果；
- 执行成功但响应丢失后不会自动重复执行；
- reconcile 能恢复已生效和未生效两种情况；
- 每次操作都有 actor、Trace 和审计事件。

## 验收命令

```bash
bun run commerce:typecheck
bun run commerce:test
bun run commerce:demo:proposal --from-report <report_id>
bun run commerce:approve --proposal <proposal_id>
bun run commerce:execute --proposal <proposal_id>
bun run commerce:execute --proposal <proposal_id>
bun run commerce:reconcile --proposal <proposal_id>
```

第二次 execute 必须返回首次结果或明确的已执行状态，不能再次改变 Mock 平台状态。

## 完成门槛

- Proposal、Approval、Execution 和 Audit 均已持久化；
- 人工审批入口独立于模型工具；
- 未审批时无法产生任何写副作用；
- Mock 执行可展示执行前后差异；
- 并发、重试、响应丢失和 UNKNOWN 核对均有自动化测试；
- 审计链可从 Proposal 追溯到报告、Trace、Evidence、审批人和执行结果；
- 进度文档已记录一条成功、一条拒绝、一条 UNKNOWN 恢复案例。

## 禁止事项

- 不连接淘宝、京东、抖音、小红书或其他真实商家写接口；
- 不将 approve、reject、execute 暴露为模型可调用工具；
- 不用内存 Map 代替持久化状态机；
- 不通过简单布尔值代替条件状态迁移；
- 不在 UNKNOWN 状态下自动重试写操作；
- 不允许修改 Proposal 后沿用旧审批。

## 交给下一链路的产物

- 可持久化的审批与执行状态机；
- 独立人工审批入口；
- Mock 平台和有限写动作；
- 幂等、并发、审计与核对机制；
- 可用于故障注入的完整执行链路。
