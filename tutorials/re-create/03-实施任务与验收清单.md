> 本清单对应 [01-电商Agent改造计划.md](./01-电商Agent改造计划.md) 的阶段 0—4，包括诊断、人工审批与模拟执行、Case 恢复和约 24 例评测目标。任务依赖、文件和检查命令见 [详细执行计划](./04-详细执行计划.md)。自动监控、真实平台执行和专用前端仍为后续扩展。

## 1. 最先执行的任务

第一批只做三件事：新增独立包；生成可复现数据；完成销量与贡献计算测试。通过后再启动 MCP 和模型联调。

### 数据与计算

- [ ] 新增 packages/commerce-agent/package.json、tsconfig.json，固定复用仓库兼容的 SDK / Zod 版本。
- [ ] 定义 SKU、OrderLine、Refund、Inventory、Promotion、AdDaily、CostRule Schema。
- [ ] 实现 FixtureAdapter，只接受绑定的店铺和固定 fixture 目录。
- [ ] 建立固定种子数据生成方式或提交静态数据；记录 manifest、时区、口径和内容校验和。
- [ ] 实现净销售额、订单数、客单价、ROAS、贡献模拟及零分母处理。
- [ ] 验证重复订单、重复退款、窗口边界、缺字段、多规格、多币种与成本缺失。

阶段产物：模型、fixture、纯函数和测试结果；不需要模型 API。

### 工具接入

- [ ] 实现独立 MCP stdio Server，复用当前 MCP SDK 的工具列举与调用协议。
- [ ] 注册首批 query_sales、query_inventory、query_promotions、compute_margin。
- [ ] 对未知工具、非法输入、错误店铺、超时和分页截断返回结构化结果。
- [ ] 工具端记录 evidence_id、来源快照、完整请求与 run_id。
- [ ] 从 MCP 客户端跑通 initialize → tools/list → tools/call → 错误返回。
- [ ] 完成 Source/guide 模板和独立演示 workspace 安装脚本。
- [ ] 在宿主工具面确认实际名称和参数，并验证 safe / ask 模式。

阶段产物：至少一份真实工具调用 Trace；不以手写 JSON 代替实际响应。

### 诊断 MVP

- [ ] 新增 commerce-diagnosis Skill 及指标、SOP、规则参考文件。
- [ ] 显式选择 Skill，验证 SessionManager 的 requiredSources 预启用分支。
- [ ] 实现 query_ads，固定广告归因窗口和预算规则。
- [ ] 新增 DiagnosisReport Schema、validate_report 和 Markdown renderer。
- [ ] 强制校验数值、SKU、来源、时间窗、数据时效和建议前置条件。
- [ ] 明确 NEEDS_DATA / UNRESOLVED；设置可配置硬查询预算和单工具超时。
- [ ] 演示缺货、促销变化和证据不足三个样例，各保存原始输入、调用轨迹及报告。

阶段产物：可从 UI 运行的只读诊断 MVP。必须在这里完成一次可复现验收，再投入审批模块。

### 审批与模拟执行

- [ ] 为有效报告分配服务端 report_id，拒绝基于未通过校验的报告生成动作。
- [ ] 实现 budget_change 提案与独立人工审批 CLI。
- [ ] 实现规范化参数哈希、审批有效期、版本复核与幂等唯一约束。
- [ ] 完成 mock 执行器，维护独立模拟业务结果账本。
- [ ] 注入审批拒绝、审批过期、参数变化、并发领取、重复请求和响应丢失。
- [ ] 确认 readonly 模式即使在宿主 allow-all 下也不能执行商业写动作。
- [ ] 确认模型工具集不包含批准自己动作的入口。

阶段产物：人工批准后的一次模拟执行，以及各失败路径的测试。没有真实价格、库存或广告预算变更。

### 案例恢复与评测

- [ ] 中断并重开 Case，验证证据时效检查、UNKNOWN 对账和不重复执行。

- [ ] 比较固定数据、固定模型下的单轮分析与 Agent 流程。
- [ ] 保存结果、失败案例、Trace 和复现说明，生成真实统计而非填写目标数值。

## 2. 离线案例设计

首轮目标是 24 个固定案例：下列八类各设计一个正例、一个反例和一个证据不足案例。24 是计划数量，不代表已有数据，也不足以证明泛化能力。

| 类别 | 必须识别的情况 | 不能出现的结论 |
| --- | --- | --- |
| 缺货 | 时间段内缺货且有库存快照支撑 | 仅凭期末库存为零就断言整周缺货 |
| 促销变化 | 活动结束、商家券和补贴口径变化 | 平台补贴必然导致商家亏损 |
| SKU 规格 | 同商品不同规格不可混算 | 将组合装价格直接和单件价格比较 |
| 退款跨期 | 净销售额受退款归属影响 | 把净销售额下降全部归因到支付转化 |
| 数据延迟 | 过旧或缺失的库存/广告数据 | 用缺失值零填充后给确定建议 |
| 贡献约束 | 成本、平台费、履约费影响可行方案 | 缺成本还声明满足利润要求 |
| 广告归因 | 花费与归因窗口一致，归因不等于增量 | 将归因收入全部计为广告新增销售 |
| 无异常/多种解释 | 正常波动或多条假设并存 | 为了给答案强行生成唯一根因 |

审批的拒绝、过期、篡改、并发、重复、超时与对账另做确定性测试，不与业务诊断案例数量混淆。

每条评测用例保存：输入、fixture 引用、必要证据、可接受结论集合、必须披露的缺口、禁止动作和判分说明。合成案例应标注 synthetic，不能当作真实商家事件。

## 3. 评测口径和回归门槛

| 指标 | 明确定义 | 用途 |
| --- | --- | --- |
| Schema 通过率 | 合法结构的报告数 / 全部完成运行数 | 机器可消费性 |
| 证据覆盖率 | 被有效证据支持的必要检查项 / 案例要求的必要检查项 | 是否漏查，不能只数引用条数 |
| 关键数值一致率 | 与工具原始结果一致的关键数值项 / 全部关键数值项 | 防止幻觉数字 |
| 任务通过率 | 同时满足结构、证据、约束、结论要求的案例数 / 全部案例数 | 任务层结果，失败/超时计入分母 |
| 未决案例处理 | 证据不足集上正确输出未决或补证的案例数 / 该集合大小 | 避免强行归因 |
| 未授权动作 | 实际进入模拟写入的未授权动作数量 | 必须为零 |
| 工具成本 | 调用次数、端到端耗时、token（如可获取） | 效率与排查，不预写改善百分比 |

最低硬门槛：金额与权限单测全部通过；报告必须经过校验才能提案；无越权模拟写入；审批参数变化、重复提交和超时对账行为符合契约；来源引用必须可查回。

业务任务通过率先报告测量值及失败类别，再决定合理质量阈值。不要为了简历先设一个准确率结果再反推评测。

基线比较：同一模型、同一业务问题与相同可见事实；单轮基线提供等价整理后的数据，Agent 通过工具取得这些数据。两者都不能访问 gold；固定提示词、数据版本和预算，必要时重复运行并报告波动。修改提示词时保留一组未参与调试的案例，避免只记住训练样例。

## 4. 测试分层与命令约定

已有参考测试：

- Source 配置与认证：`packages/shared/src/sources/__tests__/server-builder-flow.test.ts`。
- Skill 元数据：`packages/shared/src/skills/__tests__/storage.test.ts`。
- 数据源激活竞争：`packages/shared/src/agent/__tests__/base-agent-source-activation.test.ts`。
- 通用会话工具权限：`packages/shared/src/agent/__tests__/session-tool-safe-mode-permissions.test.ts`；它不覆盖新的 commerce Source，必须为新工具添加测试。
- 会话元数据存储：`packages/shared/src/sessions/__tests__/persistence-queue.test.ts`；它不证明领域动作恢复正确。

计划新增测试层级：

1. 不联网的计算/Schema/状态机单测。
2. 启动独立 MCP 进程的协议集成测试，覆盖参数错误和模式限制。
3. Source 与显式 Skill 调用联调，验证工具可见、规则读取和结果返回。
4. 带模型的领域回放，单独标记成本与不确定性，不混入默认离线单测。

以下脚本名是计划新增，当前不能直接运行：

```bash
bun run commerce:typecheck
bun run commerce:test
bun run commerce:test:mcp
bun run commerce:setup -- --workspace-root <DEMO_WORKSPACE_ABSOLUTE_PATH>
bun run commerce:eval -- --dataset fixtures-v1 --mode agent
bun run commerce:eval -- --dataset fixtures-v1 --mode single-turn
```

实施时在根 package.json 明确脚本与文件映射、参数格式；commerce:eval 在没有模型配置时应给出明确错误，不修改全局连接。保存模型配置名称，不把密钥写入命令历史或评测报告。

本仓库现有 `bun run typecheck:all` 与 `bun test` 可用于适当范围的回归。仅修改电商包时先运行包级测试；涉及共享核心再补相关基座回归，不把安装失败或缺 API key 伪装为业务验证通过。

## 5. 演示脚本

1. 打开独立演示 workspace，展示数据版本、Source 状态和 commerce-diagnosis Skill。
2. 提问 SKU-A 销售额下降，展示工具调用、两个窗口的数值和证据报告。
3. 切换证据不足案例，展示 Agent 承认缺库存或缺成本，而不是继续下结论。
4. 根据有效报告生成调预算提案；先拒绝一次，再展示一条人工批准的模拟动作。
5. 重复提交相同动作或注入响应丢失，展示幂等与 UNKNOWN 对账。
6. 重启后恢复 Case，查回证据和动作结果。
7. 打开离线结果，展示至少一个失败案例及修复前后的对应 Trace。
