# 电商数据、工具与审批契约

> 业务范围以 [01-电商Agent改造计划.md](./01-电商Agent改造计划.md) 为准，执行顺序见 [详细执行计划](./04-详细执行计划.md)。销售、退款、库存、促销、成本、广告和报告校验构成诊断链路；后续按同一计划实现人工审批、模拟动作账本及恢复。真实平台写入仍不在阶段 0—4 范围内。

本文件规定后续实现的接口与约束。所有 TypeScript 类型、JSON 和配置均为设计示例；尚未创建对应业务模块，也未执行下面的工具链路。

## 1. 数据范围和统计口径

首版固定一个演示店铺，支持同店铺不同 SKU；商品与 SKU 分开，规格必须精确匹配。请求中的店铺 ID 只是查询对象，服务端允许的店铺范围由启动配置绑定。禁止通过改变参数读取其他店铺。

| 数据实体 | 必需字段 | 首版约束 |
| --- | --- | --- |
| SKU | shop_id、product_id、sku_id、spec、currency | 组合装与单品不能自动视为同一 SKU |
| OrderLine | order_id、sku_id、paid_at、quantity、paid_amount_minor | paid_amount 为该行实付总额，已经分摊商家优惠，不能再扣一次券 |
| Refund | refund_id、order_id、sku_id、refunded_at、amount_minor | 默认按退款发生时间归入窗口；与其他退款口径明确区分 |
| InventorySnapshot | sku_id、observed_at、available_qty、locked_qty | 单个期末快照不能证明整周库存情况 |
| Promotion | promotion_id、sku_ids、start/end、kind、stacking_rule、sponsor | 会员价、商家券、平台补贴分别记录 |
| AdDaily | campaign_id、sku_id、date、spend_minor、attributed_revenue_minor、attribution_window | 广告归因收入不能当作增量收入 |
| CostRule | sku_id、effective_from/to、unit_cost_minor、fee_rate、fulfillment_cost_minor | 缺成本时不允许生成“满足毛利”的结论 |

统一规则：

- 时间窗使用 `[start, end)`，两个窗口时长和时区一致；默认演示时区 Asia/Shanghai，底层比较使用绝对时点。
- 金额为 CNY 分等最小货币单位整数；检查 JS 安全整数范围，超限拒绝或显式采用字符串/BigInt 内部表示，不直接序列化 BigInt。
- 净销售额 = 窗口内实付金额 − 同口径退款金额。支付 GMV 与净销售额分别输出，不能混称。
- ROAS = 广告归因收入 / 广告花费；花费为零时返回不可计算，不返回 Infinity。指标旁显示归因窗口。
- 首版毛利模拟针对新增销售方案，定义“单位贡献 = 单位结算收入 − 商品成本 − 平台费用 − 履约成本 − 选定口径的广告摊销”。字段名采用 contribution，避免误称会计毛利。
- 平台补贴是否进入商家结算需显式输入；无法获得结算口径时，不推断补贴等于利润。
- 模型只消费计算工具给出的数字。解释销量变化时先比较支付订单、客单价和退款，再检查库存、促销及流量；不把相关性写成已证明的因果。

## 2. Adapter 边界

建议先定义与模型和 MCP 无关的接口，再封装工具：

```ts
interface CommerceAdapter {
  sales(query: SalesQuery): Promise<SalesSnapshot>;
  inventory(query: InventoryQuery): Promise<InventorySnapshot[]>;
  promotions(query: PromotionQuery): Promise<PromotionRecord[]>;
  ads(query: AdsQuery): Promise<AdSnapshot>;
  costRules(query: CostQuery): Promise<CostRule[]>;
}
```

以上类型都需要新增。FixtureAdapter 只读取服务端指定数据目录，不能接受模型提供的任意文件路径。真实 API Adapter 后续实现同一接口，处理鉴权、限流、重试、分页与字段映射；工具协议不随数据源变化。

成本规则由受控 Adapter 加载；compute_margin 接收成本证据引用，而不是直接相信模型传入的成本数值。模型可以提交候选售价或预算，但不能借此改写库存、成本或已审批事实。

## 3. 统一请求与响应

查询请求示例：

```json
{
  "run_id": "demo-run-001",
  "case_id": "demo-case-001",
  "shop_id": "demo-shop",
  "sku_ids": ["SKU-A"],
  "window": {
    "start": "2026-09-01T00:00:00+08:00",
    "end": "2026-09-08T00:00:00+08:00",
    "timezone": "Asia/Shanghai"
  },
  "as_of": "2026-09-08T09:00:00+08:00",
  "currency": "CNY",
  "limit": 100
}
```

run_id / case_id 用于关联，不提供身份权限。校验时间、数量上限、SKU 与店铺范围；ID 只能作为受校验的键，不能直接拼接文件路径。查询执行时间和数据观察时点分开。

返回示例中的数值为合成示意：

```json
{
  "status": "ok",
  "evidence_id": "evidence-sales-001",
  "source_id": "fixture-v1-sales",
  "snapshot_version": "fixture-v1",
  "observed_at": "2026-09-08T00:00:00+08:00",
  "retrieved_at": "2026-09-08T09:00:00+08:00",
  "metric_definition": "net_sales_refund_event_time_v1",
  "currency": "CNY",
  "data": {
    "paid_amount_minor": 120000,
    "refund_amount_minor": 20000,
    "net_sales_minor": 100000
  },
  "warnings": [],
  "truncated": false,
  "next_cursor": null
}
```

每份 evidence 在服务端关联完整规范化请求、记录来源和快照校验和；不能仅保存一个没有数据对应关系的字符串 ID。相同快照的 ID 稳定，真实刷新产生新版本。

status 支持 ok / missing / stale / partial / conflict / unauthorized / timeout / rate_limited / invalid_input。missing 和 partial 属于数据质量状态；协议执行失败另设置 MCP isError。SDK 返回体按当前项目 MCP SDK 支持的格式实现，至少保证 text content 中包含合法 JSON；不要求宿主支持未经验证的新返回扩展。

缺失值用 null 或显式状态，不能用 0 替代；部分结果必须明确覆盖范围。分页由调用方继续查询，不能仅凭第一页生成全量结论。

## 4. 工具列表与业务动作

| 工具 | 关键输入 | 关键输出 | 阶段 |
| --- | --- | --- | --- |
| query_sales | SKU、窗口、口径 | 实付、退款、净销售额、订单数 | 1 |
| query_inventory | SKU、窗口、最大可接受数据年龄 | 库存快照、缺货区间证据 | 1 |
| query_promotions | SKU、窗口 | 活动区间、叠加规则、补贴方 | 1 |
| compute_margin | 售价方案、成本与促销 evidence_refs | 可复现计算明细、约束是否满足 | 1 |
| query_ads | SKU、窗口、广告计划 | 花费、归因收入与窗口 | 2 |
| validate_report | 报告草稿、当前 Case | 校验问题、服务器生成的 report_id 和 report_hash | 2 |
| propose_action | 有效 report_id、动作类型、参数 | 待审批 action_id、约束检查结果 | 3 |
| get_action_status | action_id | 审批/执行状态和实际结果引用 | 3 |
| get_case | case_id | 已存证据引用、报告和任务阶段 | 4 |

首版工具集只包含当期已完成的工具。propose_action 即便不写真实业务数据，也会写提案记录，不能当作普通只读查询随意放行。validate_report 先实现纯校验；阶段 3 需要持久化有效报告时，应明确为服务端审计写入并重新检查工具权限分类。

不能仅按 query / get 前缀判断只读；工具内部按注册清单分发，未知工具拒绝。MCP 进程记录审计副作用不改变商业查询的只读属性，但须和更改预算等业务写入区分。

## 5. 报告契约与流程

```ts
type DiagnosisReport = {
  case_id: string;
  scope: { shop_id: string; sku_ids: string[]; baseline_window: TimeWindow; current_window: TimeWindow };
  status: 'RESOLVED' | 'NEEDS_DATA' | 'UNRESOLVED';
  observations: Array<{ statement: string; evidence_refs: string[] }>;
  hypotheses: Array<{
    explanation: string;
    supporting_evidence: string[];
    opposing_evidence: string[];
    confidence_reason: string;
  }>;
  missing_data: string[];
  recommendations: Array<{ action: string; prerequisites: string[]; evidence_refs: string[] }>;
};
```

RESOLVED 只表示在本任务要求下完成了有支撑的诊断，不表示严格证明了现实世界因果。

流程：定义范围 → 核验指标 → 查询库存与促销 → 按需要查广告 → 比较候选解释 → 验证约束 → 校验报告 → 输出。

校验器至少检查：Schema、引用存在、引用属于当前店铺/SKU/Case、两个窗口口径一致、报告数值与证据一致、过期或缺失数据是否披露、建议前置条件是否满足。语义结论仍需人工/离线真值复核，不能声称引用存在就代表结论正确。

没有足够证据时状态转 NEEDS_DATA；达到工具调用预算仍无法判定时转 UNRESOLVED。Skill 可以建议预算，但硬预算由 runner 或电商服务按 run_id 强制执行。

## 6. Source 与 Skill 安装方式

安装脚本后续应接受明确的独立演示 workspace 路径、仓库绝对路径和 Bun 可执行文件绝对路径，写入前展示目标并避免覆盖已有同名 Source。不能把个人 workspace 作为默认覆盖目标。

拟安装的 Source 配置模板：

```json
{
  "id": "commerce-demo-source",
  "name": "Commerce Demo",
  "slug": "commerce",
  "enabled": true,
  "provider": "commerce-demo",
  "type": "mcp",
  "tagline": "演示店铺经营数据查询与诊断",
  "mcp": {
    "transport": "stdio",
    "command": "<ABSOLUTE_BUN_PATH>",
    "args": ["run", "<ABSOLUTE_REPO_PATH>/packages/commerce-agent/src/server.ts"],
    "env": {
      "COMMERCE_MODE": "readonly",
      "COMMERCE_SHOP_ID": "demo-shop",
      "COMMERCE_FIXTURE_DIR": "<ABSOLUTE_REPO_PATH>/packages/commerce-agent/fixtures/v1"
    }
  }
}
```

尖括号值由后续安装脚本替换，不能直接复制运行。源码的 stdio Source 配置没有 cwd 字段，不能默认子进程在仓库根目录启动。业务路径显式传入。连接状态通过实际 source test 更新，不手动伪造 connected 或 authenticated。

workspace 结构：`sources/commerce/config.json`、`guide.md`、可选 `permissions.json`，以及 `skills/commerce-diagnosis/SKILL.md`。

拟定 Skill frontmatter：

```yaml
---
name: commerce-diagnosis
description: 调查指定店铺与 SKU 的经营异常，输出带来源的诊断报告和建议。
requiredSources:
  - commerce
---
```

Skill 正文依次引用指标说明、调查 SOP、约束规则和报告契约。不要设置 blanket alwaysAllow。在 UI 显式选中该 Skill，让请求携带 skillSlugs；仅在自然语言中写“帮我分析”不保证触发 requiredSources 自动启用。

权限接入注意：workspace 级规则可写完整工具名正则，例如 `^mcp__commerce__(query_sales|query_inventory|query_promotions|query_ads|compute_margin)$`。Source 级规则会被现有 applySourceConfig 加上 `mcp__commerce__.*` 前缀，不能把上述完整正则原样填入 Source 配置。

所有自定义允许规则都是追加到默认规则，不能视为完整隔离白名单。需要验证实际工具名、默认匹配结果及 safe / ask 行为；服务端 COMMERCE_MODE=readonly 应在所有模式下拒绝商业写操作。不要将生产凭据配置给该原型。

## 7. 动作、审批与幂等

阶段 3 先实现 budget_change，生成不可变动作提案：

```ts
type ActionProposal = {
  action_id: string;
  case_id: string;
  report_id: string;
  shop_id: string;
  kind: 'budget_change';
  target_id: string;
  params: { new_budget_minor: number; currency: string };
  params_hash: string;
  snapshot_version: string;
  evidence_refs: string[];
  idempotency_key: string;
  status: ActionStatus;
  approval: null | { approved_by: string; approved_at: string; expires_at: string; params_hash: string };
};
```

状态：DRAFT → WAITING_APPROVAL → APPROVED → EXECUTING → SUCCEEDED / FAILED / UNKNOWN；可进入 REJECTED / EXPIRED。状态变更使用事务与条件更新，例如只允许 APPROVED 转 EXECUTING，避免两个 worker 同时领取。

params_hash 由服务端对规范化参数生成，覆盖店铺、动作类型、目标、币种、预算和前置版本，不能接受模型提供的 hash 作为真值。改变参数生成新提案并重新审批。幂等键由服务端生成/验证，账本设置唯一约束；相同键不同参数拒绝。

人工审批 CLI 读取原始提案、显示动作差异和风险，确认后写审批记录。没有 MCP approve_action 工具；模型调用 propose_action 不能直接把状态设为 APPROVED。把 PreToolUse 的一次通用工具放行当作业务审批是不充分的。

mock 执行器执行前复核审批时效、参数摘要、当前模拟版本和经营约束；成功记录动作结果。故意注入“写入成功但响应丢失”时，状态转 UNKNOWN，利用幂等键查询模拟外部账本后对账。SQLite 事务与模拟外部副作用分离，测试该窗口，不能用一次 DB 事务假装解决真实远程事务。

前端审批面板是后续可选项。首版独立 CLI 的身份来自本地可信操作者假设；同权限本地进程不是强隔离安全边界。生产执行必须另设身份和授权服务，不在本计划默认启用。

## 8. Case 与 Trace

Case 保存 scope、各阶段状态、evidence_refs、报告版本、提案 ID、最后刷新时点。证据快照不可原地覆盖；读取历史案例按店铺/SKU/时间查询，不先引入向量库。

SQLite 表建议：cases、evidence、reports、actions、action_events；各表绑定店铺和 Case。文件放在指定的演示数据目录中，fixtures 与运行结果分离；禁止写入现有会话 JSONL 或 Pages store.sqlite。

恢复步骤：读取 Case → 检查证据版本/时效 → 查询动作实际状态 → 刷新必要数据 → 从合适阶段续接。对话续接不能触发已审批动作再次执行。

Trace 至少记录 run_id、case_id、step_id、tool、规范化参数摘要、evidence_refs、status、duration_ms、错误类型，以及模型/提示词/数据/工具 Schema 版本。SDK 提供 token 用量时记录；缺失则写 null，不猜测费用。

开发日志输出 stderr，stdout 只保留 MCP 协议。运行 trace 另存 JSONL；Trace 与 Case 含义不同，前者解释发生过什么，后者给出可恢复业务状态。
